# Voice Checklist

Pre-publish verification and examples of good vs bad voice.

## The Test

Before publishing, read it aloud and ask:

1. Would a tired senior engineer at 11pm get this?
2. Does every sentence earn its place?
3. Is the math concrete (~$30/run, ~30 minutes review—not "faster")?
4. Is proof before philosophy?
5. Can a skeptic verify every claim (or is it labeled unknown)?

If any answer is "no," rewrite.

## Examples

### Opening Lines

```
Bad:  "Welcome to Flow Studio, the next-generation AI-powered
      development platform that transforms how teams build software."

Good: "The job is moving up the stack. Again."
```

### Feature Descriptions

```
Bad:  "Our intelligent agent orchestration seamlessly coordinates
      multiple AI models to deliver optimal results."

Good: "Seven flows. Each step produces receipts. Kill it anytime.
      Resume with zero data loss."
```

### Calls to Action

```
Bad:  "Start your journey to AI-powered development today!"

Good: "Run `make demo-run`. See what done looks like."
```

### Concrete vs Abstract

```
Bad:  "Significantly faster development"
Good: "$30 compute vs 5 days salary"

Bad:  "Robust verification"
Good: "Exit codes, test counts, coverage percentage"

Bad:  "Seamless integration"
Good: "Three commands to run the demo"
```

### Evidence-Based Claims

```
Bad:  "Our AI produces high-quality code"

Good: "The system produces code with receipts: test results,
      coverage numbers, lint output. Judge for yourself."
```

### Respectful of Skepticism

```
Bad:  "Trust us, it works"

Good: "Don't trust us. Don't trust the AI. Trust the exit codes."
```

## Remember

**Target reader:** The exhausted Senior Engineer with 5 minutes between meetings who just wants the answer.

We're not selling software. We're explaining a transition that's already happening and showing what it looks like to navigate it well.

The voice should sound like someone who's already through to the other side, looking back and explaining the path.

## The Rule

> Apply the five-question test before publishing.
> Every example should pass a skeptic's scrutiny.
> Proof before philosophy. Always.
